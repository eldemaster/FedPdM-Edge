# Literature review: federated RUL prediction on C-MAPSS and edge devices

**Scope.** Sources were checked against publisher pages, PHM Society proceedings, PMLR, ACM, and arXiv records on 12 November 2026. BibTeX entries are included only where the paper metadata (title, authors, venue/year and DOI or arXiv identifier) could be verified. RMSE and NASA score values below are reported by the cited studies; they are not recomputed, and the different preprocessing and test protocols make them context rather than a controlled ranking.

### Resource-constrained edge evidence

Prior empirical work has measured training time, communication overhead, power, and memory on physical Raspberry Pi devices~\cite{gao2020iotedge,sebbio2023raspberrypi}. The code in this repository runs on Raspberry Pi 4 clients, but the archived result JSON contains predictive metrics rather than per-round wall time, peak RSS, power/energy, or network bytes. Model payload size calculated from parameter count is only an estimate. The scientific claim should therefore be “physically deployed on Raspberry Pi clients,” not “resource-efficient” until measured.

## Code and paper claim audit

- `client.py` and `server.py` call Flower `start_client` / `start_server` without TLS certificates or transport-security configuration. No secure aggregation or DP mechanism appears in the training path. The README's “mTLS,” “encrypted weights,” and absolute privacy language were inaccurate and have been corrected.
- The clients exchange model parameters; that does not mean raw-data disclosure is impossible. Gradient/model updates may leak training information. The coordinator also receives global scaling values calculated centrally by `compute_global_scale.py`.
- `setup_fd002.py` sorts engines by maximum lifespan and assigns the lower and upper halves to clients. This is lifespan/label skew, not an operating-condition partition. The result provenance remains unresolved because logs describe an operating-condition split. The paper should not attribute FD002 effects to operating-condition partitioning until the actual assignments for the archived runs are recovered and saved.
- `client.fit` performs local MSE training; the NASA score is evaluated after prediction, not optimized. `server.py` evaluates the official test set every round. The test metrics must not be used for tuning or model selection; if they were, a fresh held-out protocol is required.
- The nominal five seeds do not settle uncertainty or significance, especially for the high-variance FD002 NASA score. The local/central baseline code should be checked for paired initialization/data order and exactly matched training units before treating differences as causal.

## Gap analysis

The study's defensible angle is an end-to-end physical testbed with two Raspberry Pi clients and an Ubuntu coordinator. The model itself is a small conventional 1D-CNN, and FedAvg is a standard method. C-MAPSS FL, FedProx, personalization, and compact/pruned FL have prior work; FedCMAPSS now gives a much broader simulated comparison. Centralized FD002 models in published work report lower errors than the present reported FedAvg result. Therefore the study's value depends on stronger reproducibility and system-level evidence rather than claiming algorithmic novelty or SOTA prediction quality.

The current key gaps are: unverified FD002 split provenance; only two subsets and two clients; five communication rounds despite a still-descending FD002 curve; no FedProx/SCAFFOLD/FedAdam/personalized baseline; no matched centralized model under clearly fixed units and compute budget; no client-specific test results; no formal privacy control; no observed edge-resource metrics; no validation set distinct from the official test set; and no paired statistical analysis.

**Recommended short paper scope:** finish ranks 1–4, collect rank 6 while those runs execute, then add one heterogeneous split and FedProx comparison. Keep DP/secure aggregation as separately scoped future work unless the privacy mechanism and threat model can be implemented and measured within the project. The strongest resulting claim would be a reproducible physical edge evaluation with measured cost and honest privacy boundaries, rather than an optimizer novelty claim.
